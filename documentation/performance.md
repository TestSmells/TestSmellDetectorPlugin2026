# Performance — Eclipse Plugin

**Date:** 2026-10-25
**Eclipse version:** 2026-09 (Eclipse IDE for RCP and RAP Developers)
**Java runtime:** JustJ OpenJDK HotSpot JRE 25.0.4 (bundled with Eclipse)
**Machine:** Intel Core i5-8265U @ 1.60 GHz (4 cores / 8 threads), 8 GB DDR4-2400
**Plugin build:** master, post markers and preferences

## Method

Detection was timed from the start of the command handler to the point where
results are ready, using instrumentation added to `TSmellHandler`:

```
[tsDetect] Analyzed <n> test file(s) in <ms> ms
```

Each project was analyzed twice and the second figure recorded, so that JVM
class loading and engine warm-up are not counted. UI responsiveness was
assessed by attempting to scroll and click in the editor while detection ran.

### Corpus

| Project | Test files | Source |
|---|---|---|
| SmellFixture | 2 | Hand-written regression corpus (`fixtures/`) |
| Perf50 | 50 | Generated by `generate-perf-fixture.ps1` |
| Perf200 | 200 | Generated by `generate-perf-fixture.ps1` |

Each generated test file contains several deliberately planted smells, so
detection performs real analysis rather than terminating early on clean input.

## Results

| Project | Test files | Detection time | Per file | UI responsive during run |
|---|---|---|---|---|
| SmellFixture | 2 | 55 ms | 27.5 ms | yes |
| Perf50 | 50 | 296 ms | 5.9 ms | yes |
| Perf200 | 200 | 753 ms | 3.8 ms | brief stall, ~150 ms |

## Analysis

Per-file cost falls sharply as the project grows — from 27.5 ms at two files to
3.8 ms at two hundred. This indicates a fixed startup cost that dominates small
runs rather than a per-file cost that grows.

The marginal cost between the 50- and 200-file runs is roughly 3 ms per
additional test file, and scaling across that range is close to linear.
Extrapolating on that marginal rate:

| Test files | Projected time |
|---|---|
| 500 | ~1.8 s |
| 1,000 | ~3.2 s |
| 2,000 | ~6.2 s |

These are projections, not measurements, and assume linear scaling continues.

The test machine is a low-power mobile processor from 2018 with 8 GB of memory.
The figures above should therefore be read as a conservative baseline: a
developer on more capable hardware can be expected to see shorter times.

## UI responsiveness

Detection currently executes on the user interface thread, so the workbench
cannot repaint or respond while it runs. At the sizes tested this is not a
practical problem: no stall was perceptible below 200 test files, and the stall
at 200 was approximately 150 ms.

The limitation is nevertheless real and would become visible on a large
codebase, where a multi-second freeze would be unacceptable. It becomes
significantly more important if detection is ever triggered automatically on
file save, since the same cost would then be incurred repeatedly during normal
editing rather than once on an explicit user action.

No issue is filed against current behaviour. The work is instead tracked as a
prerequisite for automatic detection.

## Limitations

**The large corpora are synthetic.** The plugin pairs a test file with its
production file by removing the first four characters of the filename, so it
supports only the `testExample.java` → `Example.java` convention. The widely
used `ExampleTest.java` convention produces no match, and the run fails with a
file-pairing error rather than returning results.

This made benchmarking against a real open-source Java project impractical, and
is a limitation of the tool rather than of the measurement. It is recorded in
`documentation/regression-baseline.md` alongside the other engine findings.

**Timing covers detection only.** Rendering the results table and creating
problem markers happen after the measured window and are not included.

## Conclusion

Detection performance is acceptable for on-demand use at realistic project
sizes. The single-threaded execution model is a known limitation that does not
currently affect users, and is tracked as groundwork for automatic detection
rather than as a defect.
