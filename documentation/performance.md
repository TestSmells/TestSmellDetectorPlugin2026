# Performance — Eclipse Plugin

**Date:** 2026-10-26
**Eclipse version:** 2026-09 (Eclipse IDE for RCP and RAP Developers)
**Java runtime:** JustJ OpenJDK HotSpot JRE 25.0.4 (bundled with Eclipse)
**Machine:** Intel Core i5-8265U @ 1.60 GHz (4 cores / 8 threads), 8 GB DDR4-2400
**Plugin build:** master, post background job and results-table redraw fix

## Method

Detection is timed from the start of the command handler to the point where
results are ready, using instrumentation in `TSmellHandler`:

```
[tsDetect] Analyzed <n> test file(s) in <ms> ms
```

Each project was analyzed twice and the second figure recorded, so that JVM
class loading and engine warm-up are not counted. UI responsiveness was
assessed by scrolling and clicking in the editor while detection ran, and by
attempting to cancel the run from the progress indicator.

### Corpus

| Project | Test files | Source |
|---|---|---|
| SmellFixture | 2 | Hand-written regression corpus (`fixtures/`) |
| Perf50 | 50 | Generated by `scripts/generate-perf-fixture.ps1` |
| Perf200 | 200 | Generated by `scripts/generate-perf-fixture.ps1` |
| Perf1000 | 1,000 | Generated by `scripts/generate-perf-fixture.ps1` |

Each generated test file contains several deliberately planted smells, so
detection performs real analysis rather than terminating early on clean input.

## Results

| Project | Test files | Detection time | Per file | UI responsive during run | Cancellable |
|---|---|---|---|---|---|
| SmellFixture | 2 | 55 ms | 27.5 ms | yes | n/a — completes too quickly |
| Perf50 | 50 | 344 ms | 6.9 ms | yes | yes |
| Perf200 | 200 | 986 ms | 4.9 ms | yes | yes |
| Perf1000 | 1,000 | 4,630 ms | 4.6 ms | yes | yes |

No stall was observed at any corpus size, including the 1,000-file run.

## Analysis

Per-file cost falls sharply as the project grows — from 27.5 ms at two files to
4.6 ms at a thousand. This indicates a fixed startup cost that dominates small
runs rather than a per-file cost that grows.

Across the 200-to-1,000 range the marginal cost is approximately 4.6 ms per
additional test file, effectively identical to the per-file average at 1,000
files. Scaling is therefore close to linear, and no degradation appears as the
corpus grows by a factor of five.

The 1,000-file figure is now measured rather than projected. An earlier
estimate in this document put it at roughly 3.2 s. The measured 4.6 s is higher
because the timed window now also covers problem-marker creation and the
overhead of scheduling and reporting progress from a background job, none of
which the earlier detection-only measurement included.

The test machine is a low-power mobile processor from 2018 with 8 GB of memory.
The figures above should therefore be read as a conservative baseline: a
developer on more capable hardware can be expected to see shorter times.

## UI responsiveness

Detection runs in an Eclipse `WorkspaceJob` rather than on the user interface
thread. The workbench stays usable for the duration of a run: the editor
scrolls and accepts input, progress is reported in the status bar, and the run
can be cancelled from the progress indicator. Cancellation was verified
repeatedly at 1,000 files.

Moving detection off the UI thread initially exposed a second bottleneck that
the previous measurements had hidden. Detection itself no longer blocked the
workbench, but the interface still froze for several seconds once the progress
bar completed. The cause was `TSmellTableViewer.createTable()`, which added one
`TableItem` per detected smell in a loop; SWT re-lays out and repaints the
entire table after every insertion, so a corpus producing thousands of rows
forced thousands of full repaints. Wrapping the population loop in
`setRedraw(false)` / `setRedraw(true)` defers painting until the table is fully
built and removed the stall. The call is paired in a `finally` block so that a
file-pairing exception raised mid-loop cannot leave the view permanently
unpainted.

A smaller residual cost remains at the end of a run. A `WorkspaceJob` batches
resource change notifications and flushes them when the job completes, so all
marker additions reach the Problems view, editor rulers and file decorators in
a single burst. This is inherent to how Eclipse batches workspace changes and
is not perceptible at the sizes tested.

Because detection no longer blocks the workbench, the principal obstacle to
triggering detection automatically on file save has been removed.

## Limitations

**The large corpora are synthetic.** The plugin pairs a test file with its
production file by removing the first four characters of the filename, so it
supports only the `testExample.java` → `Example.java` convention. The widely
used `ExampleTest.java` convention produces no match, and the run fails with a
file-pairing error rather than returning results.

This made benchmarking against a real open-source Java project impractical, and
is a limitation of the tool rather than of the measurement. It is recorded in
`documentation/regression-baseline.md` alongside the other engine findings.

The same constraint bounds how much the residual marker-flush cost matters in
practice: a project large enough for it to become visible is a project the
plugin cannot pair files for in the first place.

**Timing covers detection and marker creation.** Populating the results table
happens after the measured window and is not included in the figures above.

## Conclusion

Detection performance is acceptable for on-demand use well beyond realistic
project sizes, scales linearly to at least 1,000 test files, and no longer
blocks the workbench at any size tested. The single-threaded execution model
recorded as a limitation in the previous revision of this document has been
resolved.
